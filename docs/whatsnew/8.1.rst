What's New in Astropy 8.1?

========

Astropy 8.1 is a release that adds significant new functionality since
the 8.0 release.

In particular, this release includes:

* :ref:`whatsnew-8.1-faster-table-joins`
* :ref:`whatsnew-8.1-quantity-int-config`

* :ref:`whatsnew-8.1-wcsaxes-quantities`

.. _whatsnew-8.1-time-string-formats:

Faster Time string formats
==========================

Converting a :class:`~astropy.time.Time` to one of the string-based formats
(``iso``, ``isot``, ``yday``, ``fits`` or ``datetime64``) is now done with
array operations instead of a Python loop over the individual times. For large
arrays this is more than ten times faster, which speeds up printing a ``Time``
and writing tables that contain a time column.

.. _whatsnew-8.1-faster-table-joins:

Faster Table joins
==================

The :func:`astropy.table.join` function now has the ability to use `pandas.merge
<https://pandas.pydata.org/docs/reference/api/pandas.merge.html>`_ as the internal
engine for join operations. This can speed up the join by up to ~10x for large tables
relative to astropy 8.0. This is supported with a new ``engine`` option that can have
the values ``"astropy"``, ``"pandas"``, and ``"auto"``. The ``"auto"`` mode uses pandas
if it is available and otherwise falls back to the built-in astropy join implementation.

In addition, the built-in astropy join was sped up by a factor of ~2x for the common
case of a single join column.

.. _whatsnew-8.1-quantity-int-config:

Controlling the conversion of integers by Quantity
==================================================

Creating a |Quantity| from integer input without giving a ``dtype`` upcasts the values
to float. That is often what you want since most physical quantities are continuous, but
sometimes this is not desired and in the worst case it silently loses precision for
large values that ``float64`` cannot represent exactly.

This is now controlled by a new configuration item,
`astropy.units.quantity.conf.quantity_convert_int_to_float
<astropy.units.quantity.Conf.quantity_convert_int_to_float>`, which takes one of three values: ``default``,
``always``, or ``never``. An explicit ``dtype`` argument is always honored regardless of
the configuration.

For example::

    >>> import astropy.units as u
    >>> from astropy.units.quantity import conf
    >>> with conf.set_temp("quantity_convert_int_to_float", "never"):
    ...     q = [1, 2] * u.ct
    >>> q.dtype
    dtype('int64')

There is also a :func:`~astropy.units.preserve_dtype_by_default` context manager to
preserve the input ``dtype`` unless the ``quantity_convert_int_to_float``
configuration is set to ``always``.

See :ref:`quantity-convert-int-to-float` for details.

.. _whatsnew-8.1-qtable-int-columns:

Integer columns with a unit keep their dtype in a QTable
========================================================

An integer |Column| with a unit added to a |QTable| is converted to a |Quantity|,
and that conversion used to cast the values to float. It now keeps the integer
``dtype``::

    >>> from astropy.table import QTable, Column
    >>> t = QTable({"source_id": Column([2741100559643251862], unit="")})
    >>> t["source_id"].dtype
    dtype('int64')
    >>> t["source_id"][0]
    <Quantity 2741100559643251862>

Previously the identifier above came back as ``<Quantity 2.74110056e+18>``, a
different number from the one that went in. This is an API change: code that relied on such a column
being float may need updating, and integer division or overflow behavior now
applies where floating point behavior did before.

To restore the previous behavior, set the `astropy.units.quantity.conf.quantity_convert_int_to_float
<astropy.units.quantity.Conf.quantity_convert_int_to_float>`
configuration value to ``always``, either in your configuration file or for a block of
code with :meth:`~astropy.config.ConfigNamespace.set_temp`.

.. _whatsnew-8.1-reading-int-columns:

Reading files with integer columns that have units
==================================================

Reading a file into a |QTable| goes through the same conversion, so an integer
column with a unit read from VOTable, FITS, ECSV, HDF5 or parquet now keeps its
``dtype`` rather than being cast to float.

This is strictly speaking an API change, but it is really a bug fix: the previous
behavior corrupted values that the file itself stored exactly, with nothing to indicate
that anything had been lost. Setting `astropy.units.quantity.conf.quantity_convert_int_to_float
<astropy.units.quantity.Conf.quantity_convert_int_to_float>`
to ``always`` restores the previous behavior if needed.

.. _whatsnew-8.1-pyodide-wheels:

WebAssembly (Pyodide) wheels
============================

Astropy now builds and publishes WebAssembly wheels (``pyemscripten_*_wasm32``, see
:pep:`776` and :pep:`783`) alongside its native wheels. This means ``astropy`` can be
installed with ``pip`` (for example via ``micropip``) under `Pyodide
<https://pyodide.org>`_ and PyScript, rather than relying on the copy vendored in the
Pyodide distribution.

.. _whatsnew-8.1-wcs-init:

New function to initialize a celestial WCS without a FITS file
===============================================================

A new function :func:`~astropy.wcs.utils.skycoord_to_celestial_wcs` can be used
to create a celestial WCS from a center coordinate and a field of view:

>>> import astropy.units as u
>>> from astropy.coordinates import Angle, SkyCoord
>>> from astropy.wcs.utils import skycoord_to_celestial_wcs
>>> # Initialize a celestial WCS instance without a FITS file
>>> center = SkyCoord(266.4, -29, unit="deg")
>>> fov = Angle([0.4, 0.2], unit="deg")
>>> wcs = skycoord_to_celestial_wcs(center, fov=fov,
...                                 pixel_angular_size=[-0.005, 0.005] * u.deg)

Alternatively, for finer grain control, one can also instantiate with an image shape
rather than with the desired field of view:

>>> center = SkyCoord(266.4, -29, unit="deg")
>>> image_shape = [80, 40]
>>> wcs = skycoord_to_celestial_wcs(center, pixel_shape=image_shape,
...                                 pixel_angular_size=[-0.005, 0.005] * u.deg)


.. _whatsnew-8.1-wcsaxes-quantities:

Plotting quantities on WCSAxes
==============================

|Quantity| values plotted on :class:`~astropy.visualization.wcsaxes.WCSAxes`
with a world or celestial frame transform are now converted to the world units
of the WCS. Previously the unit was dropped and the value was used as if it
were in the world units, so for example arcseconds were interpreted as degrees.
Now the following plots a point at the correct position whatever the world
units of the WCS are::

    import astropy.units as u

    ax = plt.subplot(projection=wcs)
    ax.plot(100 * u.arcsec, 50 * u.arcsec, "o", transform=ax.get_transform("world"))
    ax.scatter([10, 20] * u.arcmin, [5, 6] * u.arcmin, transform=ax.get_transform("icrs"))

Values in units that cannot be converted to the world units raise an error,
and plain numbers are still interpreted in the world units of the WCS. Quantities
in pixel units (``u.pix``) plotted without a transform are still used as pixel
coordinates.

Note that plain numbers plotted with a celestial frame transform, such as
``ax.get_transform("icrs")``, are now also interpreted in the world units of
the WCS rather than always in degrees, consistent with
``ax.get_transform("world")``. This only makes a difference for WCS with world
units other than degrees, for example a WCS created with ``preserve_units=True``
from a header in arcseconds. Passing quantities gives the correct result in
all cases.
